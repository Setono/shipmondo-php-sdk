# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A PHP SDK for the [Shipmondo API v3](https://app.shipmondo.com/api/public/v3/specification). Published as `setono/shipmondo-php-sdk`, namespace `Setono\Shipmondo\` (PSR-4, both `src/` and `tests/`). Requires PHP >=8.2. It is HTTP-client agnostic: it depends only on PSR-7/17/18 interfaces and uses `php-http/discovery` to auto-discover a concrete client (e.g. `kriswallsmith/buzz` + `nyholm/psr7` in dev).

The architecture: base-class endpoints, `Payload` requests serialized through Valinor's Normalizer, `Resource` responses carrying `$raw`, header-based pagination, typed per-endpoint search VOs, and a typed exception hierarchy (all below).

## Commands

Composer scripts (`composer.json`):

- `composer analyse` — **PHPStan at level `max`** (config `phpstan.neon.dist`, which includes Valinor's two PHPStan extensions; needs `cuyz/valinor` 2.x).
- `composer check-style` / `composer fix-style` — ECS (`sylius-labs/coding-standard`).
- `composer phpunit` — PHPUnit 10 test suite (attribute-based: `#[Test]`, `#[DataProvider]`, `#[CoversClass]`).
- `composer rector` — Rector (`LevelSetList::UP_TO_PHP_82`); `src/Response` and `src/Request` are skipped from `ReadOnlyPropertyRector`.

Run a single test: `vendor/bin/phpunit --filter it_creates_a_sales_order` or `vendor/bin/phpunit tests/Client/Endpoint/SalesOrdersEndpointTest.php`.

Mutation testing: `vendor/bin/infection` (config `infection.json.dist`; thresholds minMsi 97 / minCoveredMsi 98, just below the actual scores — new code needs tests that kill its mutants; ratchet up, never down). pcov is the local coverage driver. On PHP 8.4 (the local default) Infection's initial test run dies on deprecation output from a dependency, so lower `error_reporting` to `E_ALL & ~E_DEPRECATED` there: `php -d error_reporting=24575 vendor/bin/infection --threads=max --initial-tests-php-options="-d error_reporting=24575"`.

The user's shell aliases: `ca` (analyse), `cf` (fix-style), `cfca` (fix then analyse), `phpunit`, `infection`, `rector`.

### Dependency constraints that are load-bearing
- `cuyz/valinor: "^2.6"` — 2.5.0 fixed a memory leak in long-running processes ([CuyZ/Valinor#800](https://github.com/CuyZ/Valinor/issues/800): every registered converter or constructor was reflected again on each `map()`, and the SDK builds a mapper per mapped item), and 2.6.0 added `@valinor-return`, which `Response\NullWhenUnknown` needs. Valinor dropped PHP 8.1 in 2.3.2, so the SDK requires PHP 8.2.
- `phpstan/phpstan: "^2.2"` — **required** (not `^2.1`): Valinor's `valinor-phpstan-suppress-pure-errors` extension implements `PHPStan\Analyser\IgnoreErrorExtension`, which only exists in 2.2+. We need that extension because the `registerTransformer` closure (`NormalizerConfigurator`'s null-stripping) isn't provably pure.
- `phpunit/phpunit: "^10.5"` — 11 would now fit PHP 8.2 (12 needs 8.3); not upgraded yet.
- `firebase/php-jwt: "^7.0"` — used by `WebhookParser` (incoming-webhook verification, see below). Pinned to **v7, not v6**: v6 carries advisory CVE-2025-45769 ("short HMAC key allowed"). The flip side is that v7 **enforces a minimum HMAC key length on `decode` AND `encode`** (HS256 ⇒ ≥32 bytes / 256 bits, per RFC 7518 §3.2; hardcoded, no bypass), so the SDK applies the same 32-byte floor when creating webhooks (`WebhookRequest::$key`) and when verifying them (`WebhookParser`). Tests that sign tokens must use keys ≥32 bytes (≥48 for the HS384 case). v7 requires PHP `^8.0`, so the `--prefer-lowest` matrix resolves v7.0.0.
- PHPStan stack is wired directly (`phpstan/phpstan` + strict-rules / phpunit / webmozart-assert + extension-installer); `setono/code-quality-pack` v3 (PHP ≥8.2) would now fit, but isn't adopted.
- **Don't use `Composer\InstalledVersions`** — `composer-dependency-analyser` (the CI dependency-analysis tool) flags it as an unknown symbol. The User-Agent is a static string.

CI (`.github/workflows/build.yaml`): coding-standards + `composer validate --strict` + `composer normalize --dry-run` on 8.2; **dependency analysis via `shipmonk/composer-dependency-analyser`** (config `composer-dependency-analyser.php` ignores the unused-dependency error on the virtual `psr/*-implementation` packages), PHPStan (`composer analyse`), PHPUnit across 8.2/8.3 (lowest & highest); coverage + mutation on 8.3. Reproduce the lowest matrix locally with `composer update --prefer-lowest -W` (composer.lock is gitignored).

## Architecture

**`Client` (`src/Client/Client.php`) is the entry point and is immutable.** All collaborators (`httpClient`, `requestFactory`, `streamFactory`, `mapperBuilder`, `normalizerBuilder`) are constructor-injected (PSR-18/17 auto-discovered when omitted); there are no setters. The SDK's Valinor configuration is two configurators, `Client\MapperConfigurator` and `Client\NormalizerConfigurator` (Valinor's `MapperBuilderConfigurator` / `NormalizerBuilderConfigurator`), and the constructor applies them with `configureWith()` to every builder: its defaults and one a consumer passes, e.g. `(new MapperBuilder())->withCache($cache)`. So a consumer never configures a builder for the SDK; the static helpers that did (`Client::configureMapperBuilder()` / `registerNormalizerTransformers()`) were removed in 2.0.0-rc.3. Credentials are constructor args (`apiUser`, `apiKey`) → HTTP Basic auth on every request. Sandbox vs production is the `bool $sandbox = false` constructor arg (hosts `app.shipmondo.com` / `sandbox.shipmondo.com`, prefix `/api/public/v3`). It exposes one memoized accessor per endpoint (`paymentGateways()`, `pickupPoints()`, `salesOrders()`, `shipmentTemplates()`, `webhooks()`).

Layers, top to bottom:

1. **Endpoints** (`src/Client/Endpoint/`). Base `Endpoint` holds the client + `MapperBuilder` and provides `mapItem()` (the map + `$raw` pipeline). `ResourceEndpoint<T>` adds `getOne()` / `createOne()`; `CollectionEndpoint<T>` adds `getPage()` / `paginate()` / `getByQueryId()`, plus the protected `fetchPage(?CollectionRequestOptions, array $filters)` that `getPage()` and filtered lists (`SalesOrdersEndpoint::search()`) share; `mapPage()` stays private. Concrete leaves declare `getPath()` + `getItemClass()` and expose only the operations that resource supports. **There are no `*EndpointInterface` types or capability traits** — operations are plain methods on the leaves, tested via a fake PSR-18 client (`tests/TestDouble/ScriptedHttpClient.php`), not mocks. To add an endpoint: extend `CollectionEndpoint<T>` (or `Endpoint`), implement `getPath()`/`getItemClass()`, add the typed public methods, and wire a memoized accessor into `Client` + `ClientInterface`.

2. **`Client::request()` / `get()` / `post()` / `delete()`** — low-level HTTP. `get`/`post`/`delete` return the **decoded JSON array**; `request()` is the PSR-7 escape hatch. `resolveUrl()` guards against sending auth credentials to a non-Shipmondo host or non-default port. `post()` serializes a `Payload` via the Normalizer.

3. **DTO mapping (CuyZ/Valinor 2.x).**
   - **Read path:** Shipmondo is snake_case, so `MapperConfigurator` applies Valinor's `MapKeysToCamelCase` key converter (don't hand-roll snake→camel; it's the name `ConvertKeysToCamelCase` has had since Valinor 2.5, which deprecated the old one). `Endpoint::mapItem()` maps the decoded array as it is, so a `MappingException` names the key as Shipmondo sends it (`resource_name`, not `resourceName`), then sets `$resource->raw = $data` — the **untouched snake_case payload** (same keys as the Shipmondo docs). Only the top-level resource gets `$raw`; nested objects' data is reachable through it. The mapper (`MapperConfigurator`) uses `allowSuperfluousKeys()` (+ `allowNonSequentialList()`, date formats), so unknown API fields are ignored. It does **not** cast scalars (`allowScalarValueCasting()` was removed in 2.0.0-rc.3), so a value of another type than the field's, e.g. an id sent as `"1"`, fails to map. Instead every response field's PHP type is the one in Shipmondo's OpenAPI schema (https://app.shipmondo.com/api/public/v3/openapi.json), nullability included; compared for every `Resource` and its nested objects on 2026-11-25, and all matched. The deliberate exceptions are nullable where the schema isn't, because real responses hold `null`: `ShipmentTemplate\Parcel::$weight` (the sandbox returned `null` for 10 of 22 parcels; `getTotalSupportedWeight()` reads it as "any weight"), `PickupPoint::$address2` (the schema's own example is `null`), and the listed `Webhook`'s two enums (#20, below). Optionality isn't read from the schema: it declares `required` only for a parcel's `weight` (which Shipmondo does send, as `null`), so it doesn't say which fields of these responses may be missing. Fields the schema doesn't describe keep their type. Don't add per-field casting; type a new field from the schema. `$raw` is stamped by that plain property assignment, not a Valinor converter, and apart from `MapKeysToCamelCase`'s key converter, `MapperConfigurator` registers no converters: a conversion that belongs to one field is an attribute converter on the field (`#[AsConverter]`, e.g. `Response\NullWhenUnknown`), which Valinor detects without registration, so it holds for a consumer's own `MapperBuilder` too.
   - **Write path:** `NormalizerConfigurator` applies Valinor's own normalizer configurators `NormalizeDateTimeFormat(\DATE_ATOM)` and `NormalizeKeysToSnakeCase` (every object's keys; don't hand-roll camel→snake), and registers one SDK transformer: a `Payload` transformer that strips `null`/`[]`. `NormalizerConfiguratorTest` pins the key Shipmondo receives for every property of every `Payload`, so a property rename or a key-conversion change that moves a key fails there. Backed enums normalize to their `->value` automatically. Query VOs format their own values instead: `SalesOrderSearch` sends times as RFC 3339 **with milliseconds** (`RFC3339_EXTENDED`, Shipmondo's documented filter format), not DATE_ATOM, so a range ending mid-second keeps that second's sales orders — don't unify the two.

### Pagination is header-based
Shipmondo list endpoints return a **bare JSON array** of items and carry pagination in **response headers** (`X-Current-Page`, `X-Per-Page`, `X-Total-Count`, `X-Total-Pages`). So `Collection` (`src/Response/Collection/Collection.php`) is **never Valinor-mapped** — `CollectionEndpoint::mapPage()` maps each item individually and reads the headers off `client->getLastResponse()`. `paginate()` increments `page` until an empty page or `page >= totalPages`.

`pickupPoints` is special: `GET /pickup_points` returns a bare array with **no** pagination headers, so `PickupPointsEndpoint` extends `Endpoint` (not `CollectionEndpoint`) and `search()` returns a plain `list<PickupPoint>`. `PaymentGateways` and `ShipmentTemplates` look items up by `?id=` query param (`getByQueryId()`), not a REST sub-path; `SalesOrders::getById()` uses the REST path `/sales_orders/{id}`.

### Filtering is per endpoint
Shipmondo has no shared filter syntax: each list endpoint documents its own query parameters. So filters don't go on `CollectionRequestOptions`; an endpoint that filters takes a typed query VO (`PickupPointSearch`, `SalesOrderSearch`). `SalesOrdersEndpoint::search()` returns one page through `fetchPage()` and has no `paginate()` counterpart. Verified on the sandbox (2026-11-23): `order_id` matches exactly and case-sensitively and returns every sales order with that order id, so a search by order id fits one page; and sales orders list at most 25 per page — a larger `per_page` gets a 200 with `X-Per-Page: 25`, not an error, so don't add a client-side 25 check (`CollectionRequestOptions` allows 50 because other lists accept it). A just-created sales order is listed only after a short delay (README: eventual consistency).

## Requests, responses, exceptions

- **Requests** (`src/Request/`): `abstract Payload` is the marker the normalizer matches. The body DTOs (`Payload` subclasses) are `final` with **mutable** `public` promoted properties and **all-optional** constructor args (no construction-time `Assert`), so callers can build a request incrementally (`new SalesOrderRequest()` → assign fields → `$req->orderLines[] = $line`) or in one named-arg call; required fields are enforced server-side (a missing one → `ValidationException`). The query VOs (`CollectionRequestOptions`, `PickupPointSearch`, `SalesOrderSearch`) are the exception — they stay `readonly` + validated. One more exception: `WebhookRequest::$key` IS validated in the constructor (≥32 bytes / 256-bit floor) — not a server rule but a client-side HS256 requirement, since a shorter key could never be verified by `WebhookParser` (the property stays mutable, so the constructor check covers the named-arg path; the verify path re-checks). Native enums live in `src/Enum/`. **Naming:** the top-level request body an endpoint method accepts is suffixed `Request` (`SalesOrderRequest`, `WebhookRequest`); nested value objects (`Recipient`, `Sender`, `OrderLine`, …) and all responses stay bare (the `Request\`/`Response\` namespace carries the distinction). `PickupPointSearch`, `SalesOrderSearch` and `CollectionRequestOptions` are **query VOs (not Payloads)** with a `toArray()` of snake_case query params (a search filter left `null` isn't sent); `SalesOrdersEndpoint::search(SalesOrderSearch, ?CollectionRequestOptions)` sends both. Quirk: address `zipcode` (lowercase property name so snake-casing is a no-op) and the `vat_no` (ship_to/bill_to → `Recipient`) vs `vat_id` (sender → `Sender`) split.
- **Responses** (`src/Response/`): `abstract Resource` carries `public array $raw`. `Resource` subclasses are `final` with `public readonly` props, not `final readonly class`: `$raw` is written after mapping, so `Resource` isn't readonly, and PHP doesn't let a readonly class extend a non-readonly one (which is also why Rector's readonly-class rule leaves them alone). Response types that aren't `Resource`s, such as `Collection`, can be `final readonly class`. Domain folders are singular (`Response/ShipmentTemplate/…`). `PickupPoint` is the one response that round-trips: consumers keep a chosen pickup point, so it implements `JsonSerializable` (typed fields, never `$raw`) and has the strict inverse `fromArray()`; `Request\SalesOrder\ServicePoint::fromPickupPoint()` turns it into a sales order's service point. Consumers save pickup points and read them back after upgrading, so `fromArray()` must keep reading every saved shape in `PickupPointTest::savedPickupPoints()`: never edit those, and add one when `jsonSerialize()` changes. Breaking them is a BC break. Both the response `Webhook` and the inbound `WebhookEvent` type `action`/`resourceName`(`resourceType`) as the `WebhookAction`/`WebhookResourceName` enums. The inbound `WebhookEvent` **fails fast on an unknown value** (a `MalformedWebhookException` in the parser) rather than passing an unmodeled string through: the user prefers things to blow up when something is unexpected. The listed `Webhook` is the one exception (#20): its two enums are nullable and carry `#[NullWhenUnknown(…)]`, which maps a string the enum doesn't know to null (the original stays in `$raw`), because the webhook list holds every webhook on the account, also other integrations', and one unknown value would otherwise make the whole list unreadable. Any other field of it that doesn't fit still fails to map. `NullWhenUnknown::map()` declares its return type to Valinor as a method template (`@valinor-return T`), since Valinor applies a converter only when its return type fits the field's, while PHPStan reads the native `?\BackedEnum`; `$next` maps a known value as usual.
- **Exceptions** (`src/Exception/`): marker interface `ShipmondoException` → `ResponseAwareException` (pre-reads the body once so `getError()` works on non-seekable streams; Shipmondo errors are `{"error": "..."}`; `getRequest()` is the request as it was sent, credentials included, so every throw site passes the sent request: `get()`/`post()`/`delete()` decode with the request `send()` returns, and endpoints pass `client->getLastRequest()`) → `ClientErrorException` / `ServerErrorException` → concretes. `Client::assertStatusCode()` maps status codes via `match` (401/403/404/422/429, `>=500`, any other 4xx → `UnexpectedClientErrorException`, so every 4xx is a `ClientErrorException`; anything else, e.g. a 3xx → `UnexpectedStatusCodeException`); 2xx-but-unmappable → `MappingException` (extends `MalformedResponseException`). `Client::request()` wraps a PSR-18 `ClientExceptionInterface` in `ConnectionException` (no response; it implements both `ShipmondoException` and PSR-18's `ClientExceptionInterface`). It also reads the whole body before returning (a PSR-18 client such as Symfony's `Psr18Client` streams it, so a timeout mid-body only shows on read): when reading a 2xx body throws PSR-7's `\RuntimeException`, it throws `ConnectionException` with `getResponse()` set to that success (status + headers, empty body), since Shipmondo did what was asked but the answer is lost; for any other status it throws the status's exception with an empty body. So `catch (ShipmondoException)` nets every failure of a call, as the README's "Errors" section promises. The webhook-parsing exceptions are a **separate** branch off the marker (they carry no Shipmondo HTTP response, so they do NOT extend `ResponseAwareException`): abstract `WebhookException` → `WebhookVerificationException` (bad signature / wrong key → 401/403) and `MalformedWebhookException` (bad JSON / missing `data` / non-HS256 token → 400).

### Incoming webhook parsing (`src/Webhook/`)
Separate from the API-management `WebhooksEndpoint` (subscription CRUD), `WebhookParser` verifies and parses the webhooks Shipmondo POSTs to a consumer's server. A delivery is `{"data": "<JWT>"}` (HS256-signed with the webhook `key`) plus five `SMD-*` headers (`SMD-Resource-Type`/`-Resource-Id`/`-Webhook-Id`/`-Action`/`-User`); the verified JWT payload is `{webhook, data, url}`. `parse(ServerRequestInterface, $key)` (PSR-7) and `parsePayload(string $body, array $headers, $key)` (framework-agnostic) return a `WebhookEvent` (plain VO, NOT a `Resource`) exposing the header metadata + the `data` resource as `array<array-key, mixed>` (raw snake_case, like `Resource::$raw`). Verification pins HS256 (firebase rejects any other `alg`, incl. `none`). The parser is standalone (Client-decoupled — different secret), stateless, and the `key` is passed per call so a multi-webhook server can pick the key by `SMD-Webhook-Id`. No typed mapping of `data` (deliberate — payload shapes can drift from GET responses), and `WebhookEvent` carries **no `$raw`** (its three claims `webhook`/`url`/`data` are all already typed properties, so a `Resource`-style `$raw` would be redundant; `data` is itself the untyped escape hatch). Unlike endpoints, `WebhookParser` **does** implement an interface (`WebhookParserInterface`) — it's an injectable consumer-facing service, not a Client-internal endpoint, so the no-`*EndpointInterface` rule doesn't apply. `WebhookEvent::$action`/`$resourceType` are the `WebhookAction`/`WebhookResourceName` enums; the parser resolves the `SMD-Action`/`SMD-Resource-Type` headers via `tryFrom()` and throws `MalformedWebhookException` if missing/unknown. The resource↔action relationship is encoded on `WebhookResourceName` (`actions(): list<WebhookAction>` + `supports(WebhookAction): bool`), and `WebhooksEndpoint::create()` throws `\InvalidArgumentException` on an unsupported resource/action pair before sending (only when both are set — null fields stay server-authoritative).

## Testing conventions

- Tests mirror `src/`, extend `Setono\Shipmondo\ShipmondoTestCase` (provides `client(ScriptedHttpClient)` + `BASE`), and use PHPUnit **attributes** (`#[Test]`, `#[DataProvider]` with `public static` providers).
- Drive endpoints with `ScriptedHttpClient` (fake PSR-18 keyed by full URL, records sent requests + supports response headers; `fail()` makes a URL throw a PSR-18 network exception) — no mocking framework, no endpoint interfaces.
- PHPStan max is strict: avoid `assertInstanceOf` on already-narrowed types, and `assertIsArray()` before indexing into `json_decode`/`$raw` (both are `mixed`-valued).
- **`LiveClientTest`** hits the real API and is skipped unless `SHIPMONDO_LIVE` is `1`/`true`, reading `SHIPMONDO_USERNAME` / `SHIPMONDO_API_KEY` from the env, and `SHIPMONDO_SANDBOX` (`1`/`true`) to target the sandbox — sandbox credentials get a 401 from production. A local `phpunit.xml` (gitignored; `phpunit.xml.dist` is the committed one) can hold them as `<env>` entries; a variable already set in the shell wins over it. Never commit credentials; never enable in CI.
